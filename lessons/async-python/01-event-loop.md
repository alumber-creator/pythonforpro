# Event Loop и конкурентность в Python: GIL, потоки и процессы

## Введение

Конкурентность — одна из самых сложных и одновременно самых важных тем в современном
программировании. Python предлагает **три принципиально разные модели** конкурентного
выполнения кода, и выбор между ними определяет архитектуру всего приложения.

В этом уроке мы разберём фундамент, на котором стоит вся асинхронная экосистема Python:
- **GIL (Global Interpreter Lock)** — почему он существует и что именно защищает;
- **Потоки (threading)** — когда они работают, а когда становятся бесполезны;
- **Процессы (multiprocessing)** — настоящий параллелизм ценой изоляции;
- **Event Loop** — кооперативная многозадачность в одном потоке.

К концу урока вы будете точно знать, **почему** asyncio стал стандартом де-факто для
сетевых приложений на Python и **когда** стоит выбрать потоки или процессы.

## Основная часть

### 1. GIL: что это, зачем он нужен и что защищает

#### История вопроса

GIL (Global Interpreter Lock) — это мьютекс, который защищает доступ к внутренним
структурам интерпретатора CPython. Он существует с самых первых версий Python и
является, пожалуй, самой обсуждаемой особенностью языка.

**Почему GIL вообще появился?**

CPython использует подсчёт ссылок (reference counting) для управления памятью.
Каждый объект в Python хранит счётчик ссылок — количество мест, которые на него
ссылаются. Когда счётчик достигает нуля, объект удаляется сборщиком мусора.

```python
import sys

a = []
b = a
print(sys.getrefcount(a))  # 3: a, b, и временная ссылка в getrefcount
```

Проблема: если два потока одновременно изменяют счётчик ссылок одного объекта,
возникает **состояние гонки** (race condition). Один поток может прочитать значение,
второй — изменить, первый — записать своё (уже неверное) значение. Результат:
повреждённая память и segfault.

**Решение разработчиков CPython**: один глобальный мьютекс, который поток должен
захватить перед выполнением любого байткода Python. Это и есть GIL.

#### Что защищает GIL

GIL защищает:
- Счётчики ссылок всех объектов Python;
- Внутренние структуры интерпретатора (списки, словари, объекты типов);
- Память от повреждения при параллельном доступе.

GIL **не защищает**:
- Ваши собственные структуры данных от гонок — список `lst.append()` может
  прерваться между байткодами;
- Операции, которые выглядят атомарными, но не являются таковыми;
- Внешние ресурсы (файлы, сокеты, базы данных).

```python
# ❌ GIL не спасает от гонок на уровне приложения
import threading

counter = 0

def increment():
    global counter
    for _ in range(1_000_000):
        counter += 1  # Не атомарно! Читает, увеличивает, записывает

threads = [threading.Thread(target=increment) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()

print(counter)  # Ожидаем 4_000_000, получаем ~2_700_000 — гонка!
```

GIL обеспечивает атомарность только на уровне **одного байткода**, но операция
`counter += 1` — это несколько байткодов (LOAD_FAST, BINARY_ADD, STORE_FAST).

### 2. Потоки (threading): когда работают, когда нет

#### I/O-bound задачи — потоки эффективны

Когда поток ждёт ввода-вывода (чтение из сокета, запись в файл, ожидание ответа БД),
GIL **освобождается**. Это ключевой момент: поток, блокирующийся на I/O, отдаёт GIL
другим потокам.

```python
import threading
import time
import requests  # синхронная библиотека

def fetch_url(url):
    print(f"Начинаю загрузку {url}")
    response = requests.get(url)  # Блокирующий I/O — GIL освобождается
    print(f"Загружено {url}: {len(response.content)} байт")
    return response

urls = ["https://httpbin.org/delay/1"] * 5

start = time.perf_counter()
threads = [threading.Thread(target=fetch_url, args=(url,)) for url in urls]
for t in threads:
    t.start()
for t in threads:
    t.join()
elapsed = time.perf_counter() - start
print(f"5 потоков: {elapsed:.2f} сек")  # ~1.5 сек, а не 5 сек
```

#### CPU-bound задачи — потоки бесполезны

Если задача использует процессор (вычисления, сжатие, парсинг), GIL не даёт
другим потокам выполняться параллельно. Потоки будут выполняться **по очереди**.

```python
import threading
import time

def cpu_bound(n):
    """Вычисление чисел Фибоначчи — чистая CPU-нагрузка"""
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

# Однопоточно
start = time.perf_counter()
for _ in range(4):
    cpu_bound(300_000)
print(f"Однопоточно: {time.perf_counter() - start:.2f} сек")

# Четыре потока
start = time.perf_counter()
threads = [threading.Thread(target=cpu_bound, args=(300_000,)) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(f"4 потока: {time.perf_counter() - start:.2f} сек")  # НЕ быстрее!
```

**Результат**: потоки не ускоряют CPU-bound задачи в CPython. Напротив, накладные
расходы на переключение контекста могут сделать код **медленнее**.

### 3. Процессы (multiprocessing): настоящий параллелизм

Модуль `multiprocessing` обходит GIL полностью: каждый процесс имеет **собственный
интерпретатор Python** и собственный GIL.

```python
import multiprocessing
import time

def cpu_bound(n):
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

start = time.perf_counter()
with multiprocessing.Pool(processes=4) as pool:
    pool.map(cpu_bound, [300_000] * 4)
print(f"4 процесса: {time.perf_counter() - start:.2f} сек")  # ~в 4 раза быстрее!
```

**Цена настоящего параллелизма**:
- Процессы **изолированы**: объекты передаются через pickle (сериализацию);
- **Создание процесса** намного дороже создания потока;
- **Память**: каждый процесс имеет собственное адресное пространство;
- **Межпроцессное взаимодействие** (IPC): очереди, пайпы, разделяемая память.

```python
# ❌ Антипаттерн: multiprocessing для I/O-bound задач
# Создание 1000 процессов для 1000 HTTP-запросов — ОЧЕНЬ дорого
# ✅ Правильно: asyncio или потоки
```

### 4. Event Loop: кооперативная многозадачность в одном потоке

#### Идея

Event Loop — это бесконечный цикл, который:
1. Берёт задачу из очереди готовых к выполнению;
2. Выполняет её до первой **точки ожидания** (await);
3. Когда задача говорит «я жду», переключается на следующую;
4. Когда ожидание завершено (сокет готов к чтению, таймер истёк), задача
   возвращается в очередь готовых.

**Главное отличие от потоков**: переключение происходит не по таймеру ОС
(вытесняющая многозадачность), а **явно** в точках `await` (кооперативная
многозадачность).

```python
import asyncio

async def task(name, delay):
    print(f"Задача {name}: начинаю ожидание {delay} сек")
    await asyncio.sleep(delay)  # Точка кооперативного переключения
    print(f"Задача {name}: завершена")

async def main():
    # Запускаем три задачи «параллельно» в одном потоке
    await asyncio.gather(
        task("A", 2),
        task("B", 1),
        task("C", 3),
    )

asyncio.run(main())
# Вывод:
# Задача A: начинаю ожидание 2 сек
# Задача B: начинаю ожидание 1 сек
# Задача C: начинаю ожидание 3 сек
# Задача B: завершена          ← через 1 сек
# Задача A: завершена          ← через 2 сек
# Задача C: завершена          ← через 3 сек
# Общее время: ~3 сек, а не 6
```

#### Визуализация Event Loop

```
┌─────────────────────────────────────────────────┐
│                  EVENT LOOP                      │
│                                                  │
│  Очередь готовых ──► Выполнить ──► await? ──┐   │
│       ▲                                      │   │
│       │           ┌──────────────────┐       │   │
│       └───────────┤  I/O selector    │◄──────┘   │
│                   │  (epoll/kqueue)  │           │
│                   └──────────────────┘           │
└─────────────────────────────────────────────────┘
```

Event Loop в Python использует системный вызов `select` / `epoll` (Linux) / `kqueue`
(macOS) / IOCP (Windows) для эффективного ожидания готовности множества сокетов
**без блокировки**.

#### Почему asyncio быстрее потоков для I/O

| Характеристика | Потоки (threading) | asyncio |
|:---|---:|:---|
| Память на задачу | ~8 МБ (стек потока) | ~КБ (корутина) |
| Создание 10 000 задач | Медленно, дорого | Мгновенно |
| Переключение контекста | Ядро ОС (дорого) | Внутри процесса (быстро) |
| Гонки данных | Возможны всегда | Невозможны в одном потоке |
| Блокировка Event Loop | Нет (другие потоки работают) | Фатально (один поток) |

### 5. Сравнение моделей конкурентности в разных языках

#### Java: потоки JVM и Project Loom

Java исторически полагалась на **потоки ОС** (по одному на задачу). Потоки Java —
это «толстые» потоки: каждый требует выделенный стек ОС (~1 МБ).

```java
// Java 21: Virtual Threads (Project Loom)
// Лёгкие потоки, похожие на корутины Python
Thread.startVirtualThread(() -> {
    // Выполняется в виртуальном потоке
    // Блокирующие вызовы не блокируют поток ОС
});
```

**Ключевое отличие от Python**: в Java **нет GIL**. Потоки JVM (и виртуальные, и
платформенные) могут выполняться действительно параллельно. Project Loom добавил
лёгкие виртуальные потоки, которые **не заменяют** обычные, а дополняют их.

#### C++: std::thread и std::jthread

C++ предоставляет прямой доступ к потокам ОС:

```cpp
#include <thread>
#include <vector>

void worker(int id) {
    // Настоящий параллелизм — никакого GIL
}

int main() {
    std::vector<std::thread> threads;
    for (int i = 0; i < 4; ++i)
        threads.emplace_back(worker, i);
    for (auto& t : threads)
        t.join();
}
```

- **Плюсы**: полный контроль, настоящий параллелизм, нет GIL;
- **Минусы**: ручное управление памятью, гонки данных (UB), нет стандартного
  event loop (нужны библиотеки вроде Boost.Asio).

#### JavaScript (Node.js): однопоточный Event Loop

JavaScript в Node.js **очень похож** на Python asyncio:

```javascript
// Node.js: единственный поток, Event Loop, кооперативная многозадачность
async function fetchData() {
    const response = await fetch('https://api.example.com/data');
    return response.json();
}

// Promise.all ≈ asyncio.gather
const results = await Promise.all([fetchData(), fetchData(), fetchData()]);
```

**Отличия от Python**:
- В JS **нет GIL** (в браузере один поток, но нет блокировки);
- В Node.js асинхронность **встроена в рантайм** — всё асинхронно по умолчанию;
- В Python асинхронность — **опциональная** модель, синхронный код по умолчанию;
- JS использует libuv, Python asyncio — свой event loop (может использовать uvloop).

#### Сводная таблица: конкурентность в языках

| Язык | Модель по умолчанию | Параллелизм CPU | I/O конкурентность | Особенность |
|:---|---|---|---|---|
| **Python** | Синхронный | multiprocessing | asyncio / потоки | GIL |
| **Java** | Потоки ОС | Потоки (нет GIL) | Virtual Threads (21+) | JVM-оптимизации |
| **C++** | Синхронный | std::thread | Boost.Asio / libuv | Ручное управление |
| **JavaScript** | Асинхронный | Worker Threads | Event Loop (встроен) | Однопоточный по дизайну |
| **Go** | Горутины | Горутины (M:N) | Горутины | Встроенный планировщик |
| **Rust** | Синхронный | std::thread | tokio | Безопасность без GIL |

### 6. Когда что использовать: дерево решений

```
Вам нужна конкурентность?
│
├── Задача I/O-bound (сеть, БД, файлы)?
│   ├── Много соединений (>100)?
│   │   └── ✅ asyncio
│   └── Мало соединений (<10)?
│       └── ✅ Потоки (проще) ИЛИ asyncio
│
└── Задача CPU-bound (вычисления)?
    ├── Нужна общая память?
    │   └── ✅ multiprocessing + shared_memory
    └── Данные легко сериализовать?
        └── ✅ multiprocessing.Pool
```

### Упражнение 1: Докажите существование GIL

Напишите скрипт, который:
1. Создаёт CPU-bound задачу (вычисление хеша SHA-256 в цикле);
2. Запускает её в 1, 2, 4 и 8 потоках;
3. Измеряет время выполнения для каждого количества потоков;
4. Выводит график или таблицу, доказывающую, что время **не уменьшается**.

```python
# template/01_gil_proof.py
import threading
import time
import hashlib

def cpu_task(iterations: int) -> None:
    """Чистая CPU-нагрузка: вычисление хешей."""
    data = b"Hello, GIL!" * 1000
    for _ in range(iterations):
        _ = hashlib.sha256(data).hexdigest()

def benchmark(threads_count: int, iterations: int) -> float:
    """Замерить время выполнения в threads_count потоков."""
    start = time.perf_counter()
    threads = [
        threading.Thread(target=cpu_task, args=(iterations,))
        for _ in range(threads_count)
    ]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    return time.perf_counter() - start

if __name__ == "__main__":
    ITERATIONS = 100_000
    for n in [1, 2, 4, 8]:
        elapsed = benchmark(n, ITERATIONS)
        print(f"Потоков: {n:>2} | Время: {elapsed:.2f} сек")
```
